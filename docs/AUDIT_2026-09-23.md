## 2. Open — found, not fixed here

### HIGH — Part 2 has no end-to-end `register()`
Three modules that pass their tests are **called by no pipeline**:

| module | what it does | where it should run |
|---|---|---|
| `refine/uniformity.py::enforce` | the PS-mandated **uniform distribution** of match points | after estimation, on every registration |
| `refine/subpixel.py::refine_points` | per-point **sub-pixel** refinement | on every direct registration |
| `estimate/geometry_filter.py` (ALIGN-03) | physics-based outlier rejection | before estimation |

The TMC-2 → SELENE script only **measures** coverage (`coverage_of`); it never
enforces it. Sub-pixel refinement does run, but only inside the cascade's dense
step. Each script hand-assembles its own partial chain, so a module can be built,
tested and marked DONE without ever touching a real registration — the same
defect class as the regime selector, which had no caller until PR #13.

**This is the most important open item.** The two things the problem statement
explicitly demands — sub-pixel accuracy and uniform distribution — are not
applied on the direct registration path.

### HIGH — no CI
No `.github/workflows/`. PLAN.md's P0 CI bar and CHECK-10's GPL check are both
unmet, and `main` went red today without anyone knowing.

### MEDIUM — NAC pixel size comes from the label
ODE's `Map_resolution` is never used as a scale source. Every NAC product enters
the scale logic as the label's 0.5 m; measured reality is 0.40-1.27 m. The scale
check copes through a 3x "unverified" slack rather than knowing the right value.
**Phase 1 (TMC-2 ↔ NAC) will hit this directly.**

### MEDIUM — 39 tests skip: the data is not on this machine
After fix #10 (was 49). By reason: 17 SLDEM tiles (including 10 geometry-filter
tests, so ALIGN-03 is unexercised here), 15 MI/WAC references, 2 LOLA, 1 LOLA-or-SLDEM, 2 the
all-products pairs checks, 1 NAC `M102000149RC`, 1 other. Downloads needed:
SLDEM ~2.8 GB, LOLA ~1.9 GB, WAC (small; skip night-side products). **SELENE MI
has no fetcher in the repo**, so its tests cannot be reproduced from it at all.
`accuracy_report.py` cannot run here for the same reasons (NAC `M102000149RC`,
SLDEM).

### MEDIUM — the fine matcher sees aliased input on TMC-2 -> TC
`cv2.warpAffine` does not implement `INTER_AREA`; it silently runs bilinear
(checked: identical output). Five call sites ask for area averaging. It matters
where the warp DOWNscales: `register_tmc2_tc.py` builds the coarse template at
~0.33x and the fine-matcher input at ~0.66x with no anti-aliasing, while the TC
side is properly block-averaged, so the two sides are filtered differently. The
cascade's 1.5x step (`register_step_dense`, factor 1) has the same issue. The
measured results already include this effect, so no reported number is wrong;
fixing it (pre-blur or `cv2.resize(INTER_AREA)` first) changes numbers and must
be re-measured, not patched silently.

### MEDIUM — `build_pairs.py` cannot run on this machine
It aborts on the first reference with no footprint. The NAC products downloaded
for the illumination experiment (`M102000149LC` and eight more) carry no corners
and have no saved ODE record, so DATA-08's file cannot be rebuilt here until
those records are saved (`io.ode_client.save_product_record`, a network call).
The committed `registered_pairs.json` predates those downloads and still
reproduces from the labels (see fix #10).

### MEDIUM — 8 committed reports have no generating script in the repo
`xoftr_speed_V1/V2/V3/G1_*` (5 files) and `xoftr_speed_summary`,
`rift_vs_reference`, `tmc2_tc_gap_rows`. `score_xoftr_speed.py` only SCORES the
xoftr files. Their numbers cannot be reproduced from the repository.

### LOW — measurement caveats (numbers stand, wording should not overclaim)
- `measure_tmc2_scale.py` searches 0.90-1.12x the grid scale; the label's 4.41 m

  interior and sharp, not by scoring it (`z_label` is always None).
- Its OHRC-offset figure converts at 5.0 m/px, not the measured 4.92/5.04 (~1.5%).
- `accuracy_report.check_illumination_invariance` renders "TMC-2's sun" as
  104.3 deg az / 44.0 deg elevation: the scene-centre label values. At the patch
  (~0 N, 23.5 E) it is 92.6 / 46.3. Same class of mistake as §3 row 2 below;
  re-run once SLDEM is present.
- `cascade_ohrc_tc.json` was produced with `--windows 9`; the default is 3 and
  the report does not record its command.
- `docs/FEATURE_GUIDE.html` (hand-written judge Q&A) still describes the polar
  path and LightGlue as default.

### LOW

  ALIGN-02), `cascade.register_step`, `projection.scene_crs_for`,
